# 06 · 跨平台与打包

> 目标：理解怎么从源码得到一个“双击就能用”的程序，以及为什么三台机器要打三次包。
> 这篇的每一条注意事项背后都有一次真实翻车。

---

## 1. 先接受一个事实：不能交叉编译

PyInstaller **不支持交叉编译**。要 Windows 包就在 Windows 上构建，要 macOS 包就在 Mac 上构建，
Linux 同理。所以 `build.sh` 的设计前提是：**在目标平台上运行它**。

另一个反直觉的点：

> 决定产物架构的是**你用的 Python 解释器**，不是机器硬件。

比如 M 系列 Mac 上装了 Intel 版 Python，打出来就是 x64 包——
反而能同时跑在 Intel 和 M 系列上（M 走 Rosetta 2）。反过来的 arm64 包只能在 M 系列跑。

---

## 2. 平台差异收拢到一个文件

项目把差异全部集中在 `gui/platform_utils.py`，核心脚本零平台绑定。

| 差异项 | Windows | macOS | Linux |
| --- | --- | --- | --- |
| 浏览器探测 | `C:\Program Files\...` | `/Applications/...` | `which google-chrome` 等 |
| 打开目录 | `os.startfile` | `open` | `xdg-open` |
| 内核缓存目录 | `%LOCALAPPDATA%\ms-playwright` | `~/Library/Caches/ms-playwright` | `~/.cache/ms-playwright` |
| pywebview 后端 | WebView2 + pythonnet | WKWebView (cocoa) | GTK / Qt |

`find_browser()`（`gui/platform_utils.py:79`）按顺序找 Chrome → Edge → PATH 里的浏览器，
返回 `(路径, channel)`。`channel` 直接传给 Playwright 的 `launch_persistent_context`。

这个集中化带来的好处：`GuiBridge` 里只写 `from platform_utils import find_browser`，
完全不出现 `if sys.platform == ...`。以后加平台只改一个文件。

---

## 3. 为什么不打包浏览器内核

Chromium 内核约 **437MB**，打进去会让安装包体积失控。
项目的取舍是：

- **打包** playwright 的 driver（node 运行时 + CLI，约 103MB）—— 这是驱动浏览器必需的
- **不打包** 浏览器内核 —— 运行时优先探测本机 Chrome/Edge，都没有再回退到用户自装的 playwright 内核

`gui/app.py` 的 `_patch_frozen_paths()`（`:26`）负责打包后的路径修正：

```python
if not getattr(sys, "frozen", False):
    return
# driver 目录被收进 _MEIPASS，但 playwright 默认按 site-packages 相对路径找
os.environ.setdefault("PLAYWRIGHT_DRIVER_PATH", str(driver))
# 内核目录指向用户本机缓存
os.environ.setdefault("PLAYWRIGHT_BROWSERS_PATH", str(browsers))
```

实测成品体积约 **128MB**（含同级 `_internal` 目录），而不是 1GB+。

## 4. `build_exe.spec` 的三段结构

```
Analysis   → 收集依赖、数据文件、隐式导入
EXE        → 生成主程序（exclude_binaries=True，依赖外置）
COLLECT    → 把 exe + 依赖收进 dist/<name>/ 目录
BUNDLE     → 仅 macOS：包成 .app
```

几个关键配置：

**隐式导入**（`:113`）：PyInstaller 的静态分析看不出动态导入，
所以要手写 `hiddenimports`——playwright、webview 各平台后端、httpx 全家桶都要列上。

**Py webview 按平台分**（`:86-106`）：

```python
if IS_WINDOWS:
    webview_hidden += ["webview.platforms.edgechromium", "webview.platforms.winforms",
                       "clr", "pythonnet", "clr_loader"]
elif IS_MACOS:
    webview_hidden += ["webview.platforms.cocoa"]
    webview_hidden += ["objc", "Foundation", "AppKit", "WebKit", "PyObjCTools"]
else:
    webview_hidden += ["webview.platforms.gtk", "webview.platforms.qt"]
```

macOS 用系统自带的 WKWebView，所以**不需要 pythonnet**——这也是 Windows 包比 mac 包多几个依赖的原因。

**排除项**（`:127`）：`numpy` / `pandas` / `PIL` / `tkinter` / `unittest` 一律排除，减小体积。

**BUNDLE**（`:166`）：只有 macOS 段会生效，带 `bundle_identifier` 和 `info_plist`
（含下载目录访问权限说明）。Windows/Linux 下 PyInstaller 会忽略它。

**架构**（`:45-57, 157`）：默认跟随解释器，可用环境变量覆盖：

```bash
TARGET_ARCH=universal2 python -m PyInstaller build_exe.spec
```

但 universal2 要求**所有二进制依赖都有双架构代码**。项目依赖里 PyObjC 和 playwright 官方有
universal2 版，`cffi` 等却是分架构的——所以稳妥路线是用 universal2 版 Python
（python.org 官网安装包）配合构建。

## 5. `build.sh`：自检 + 构建 + 命名

```bash
./build.sh --check    # 只自检，先跑这个
./build.sh            # 自检 + 构建
./build.sh --clean    # 清理旧产物后构建
```

自检覆盖 6 类（`:121-245`）：

1. 平台 / 架构 / Python 版本 / 产物形态
2. 核心依赖 `playwright` / `httpx` / `webview`
3. `pyinstaller` 是否安装
4. 本机浏览器或 playwright 内核（二者有其一即可）
5. 关键文件是否齐全
6. spec 的 BUNDLE 配置 + 源码语法检查（`ast.parse`）

### 架构命名规则

脚本检测解释器架构后自动给产物改名（`:291-333`）：

| 平台 | 架构 | 产物 |
| --- | --- | --- |
| macOS | Apple Silicon | `dist/xhs-video-downloader-arm64.app` |
| macOS | Intel | `dist/xhs-video-downloader-x64.app` |
| macOS | 双架构 | `dist/xhs-video-downloader-universal2.app` |
| Windows | x64 | `dist/xhs-video-downloader-x64/xhs-video-downloader-windows-x64.exe` |
| Linux | x64 | `dist/xhs-video-downloader-x64/xhs-video-downloader-linux-x64` |

macOS 的 `.app` 是自包含目录，直接整体重命名；
Windows/Linux 的 exe 必须和同级 `_internal/` 配套，所以**先重命名整个输出目录，再改目录内 exe 的名字**。

## 6. ★ 最大的陷阱：`build/` 里的同名 exe 点不得

PyInstaller 会在 `build/` 和 `dist/` 各生成一个**同名 exe**，字节数还一样。
但 `build/` 里那个**没有同级 `_internal/` 目录**，运行时报：

```
Failed to load Python DLL '...\build\build_exe\_internal\python311.dll'
LoadError: 找不到指定的模块。
```

而且这是 GUI 程序，报错弹窗里的内容**不会写进 stdout**，只能靠报错里的路径定位。

`build.sh` 的三重防御：

1. 构建结果里用醒目提示指明 `final_path` 才是成品
2. 明确警告不要运行 `build/` 下的同名文件
3. 构建完成后**自动清理 `build/`**（它只是编译缓存，删掉不影响 `dist/`）

体积统计也要注意：`du` 必须统计整个产物目录，只算 exe 会得到 7MB 的假数字（实际 128MB）。

## 7. 图标：原创而不是官方 logo

资产在 `assets/`：

```bash
python assets/make_icon.py      # 生成 icon.png / icon.ico / iconset
# macOS 额外：
iconutil -c icns assets/icon.iconset -o assets/icon.icns
```

设计是**正红 `#ff2442` + 白色下载箭头**，视觉上贴近小红书风格，但**不使用官方 logo**，
规避商标风险。`build_exe.spec` 按平台自动选 `.ico` / `.icns`。

## 8. macOS 专属：Gatekeeper

自己构建的 `.app` 没签名，首次打开会被系统拦：

```bash
xattr -cr /path/to/xhs-video-downloader-arm64.app
```

长期分发正道是 `codesign` + `notarytool` 公证。细节见 [docs/BUILD-macOS.md](../docs/BUILD-macOS.md)，
里面有 9 项自检清单、常见问题和结果记录表。

## 动手实验

1. 跑 `./build.sh --check`，逐条对照输出，确认架构标签与你的 Python 解释器一致。
2. 构建后同时打开 `build/` 和 `dist/`，对比 exe 大小与同级目录，亲眼看 `_internal/` 的差别。
3. 用 `du -sh dist/<产物目录>` 和 `du -sh dist/<产物目录>/<exe>` 对比体积。
4. 查看 `assets/make_icon.py`，改一个颜色常量重新生成图标，再构建验证打包时能带上。

---

## 小结

- 各平台各自构建；产物架构由 Python 解释器决定
- 平台差异集中在 `gui/platform_utils.py` 一个文件
- 不打包内核（437MB），只打包 driver（103MB），成品约 128MB
- `BUNDLE` 段只管 macOS `.app`；Windows 的 pywebview 需要 pythonnet
- **只运行 `dist/` 里的成品，`build/` 里的同名 exe 是陷阱**
- 图标用原创设计，避免商标风险

最后一篇：怎么保证这些代码不被改坏，以及出问题时怎么定位。
