# 07 · 测试策略与排错

> 目标：建立分层测试的思维，知道每一层能抓什么、不能抓什么；出问题时有系统地缩小范围。
> 这套项目没有接小红书真站做自动化测试——那既不稳也不合规。它用的是**本地 Mock + 真实浏览器内核**。

---

## 1. 四层测试

| 层 | 文件 | 数量 | 抓什么 | 依赖 |
| --- | --- | --- | --- | --- |
| 纯函数单测 | `tests/test_unit.py` | 14 | 文件名清理、ID 解析、流选择、状态读写、待处理过滤、JSON 递归查找 | 无浏览器 |
| 集成测试 | `tests/test_integration.py` | 9 | 详情页 SSR 提取、接口兜底、列表合并、下载与断点续传 | 本地 HTTP server + chromium |
| GUI 逻辑回归 | `gui/test_finish_once.py`、`gui/test_toast_flash.py` | 2 组 | 完成提示去重、toast 定时器累积 | Python + JS 环境 |
| GUI 端到端 | `gui/selftest.py` | 2 种模式 | 真实窗口跑单条下载 / 账号 list-only | 真实浏览器 + 登录态 |

运行方式全在 README「运行测试」一节：

```bash
python tests/test_unit.py
python tests/test_integration.py
python gui/selftest.py            # 单条模式
python gui/selftest.py account    # 账号 list-only
python gui/test_finish_once.py
python gui/test_toast_flash.py
```

> **GUI 端到端测试前先杀残留 chrome 进程**，否则 profile 被占用会导致
> `TargetClosedError`——看起来像功能坏了，其实是测试环境脏。

## 2. 单元测试：把纯逻辑钉死

`tests/test_unit.py` 全是 `unittest.TestCase`，没有 async、没有浏览器。
几个值得学的用例设计：

**边界值**：

```python
self.assertEqual(x.sanitize_filename("   "), "untitled")
self.assertEqual(len(x.sanitize_filename("标题" * 30)), 60)
```

**优先级规则**（h264 即使分辨率低也要赢）：

```python
stream = {
    "h264": [{"master_url": "https://cdn/720.mp4", "height": 720}],
    "h265": [{"master_url": "https://cdn/1080.mp4", "height": 1080}],
}
self.assertEqual(x.pick_best_stream(stream)["master_url"], "https://cdn/720.mp4")
```

**损坏输入不崩**：

```python
path.write_text("{broken json", encoding="utf-8")
state = x.DownloadState.load(path)
self.assertEqual(state.downloaded, {})
```

**递归深度保护**：

```python
deep = ...
for _ in range(30):   # 超过 12 层
    current["child"] = {}
...
self.assertIsNone(x.find_in_json(deep, ...))
```

这些测试的价值在于：**改提取规则时立刻知道有没有破坏既有约定**。
比如把 h264 优先级改掉，`test_pick_best_stream` 立刻变红。

## 3. 集成测试：本地 Mock 页面 + 真浏览器

`tests/test_integration.py` 的思路很聪明：不连小红书，而是**自己造一个假页面**，
在页面里注入和真站一样结构的 `window.__INITIAL_STATE__`，然后用真实 chromium 打开它。

核心组件：

- `_LocalFileServer`（`:127`）—— 基于 `SimpleHTTPRequestHandler` 的本地 HTTP server，
  提供假 HTML 和假视频文件
- `_detail_html(note)`（`:41`）—— 生成带 `__INITIAL_STATE__` 的详情页 HTML
- `_launch_browser(p)`（`:26`）—— 用 playwright 的 chromium 打开本地页面
- `_QuietHandler`（`:122`）—— 屏蔽 HTTP server 的默认日志，输出干净

九个用例覆盖：

| 用例 | 验证什么 |
| --- | --- |
| `test_video_note_stream` | 从 SSR 内嵌数据里提出视频流 |
| `test_image_note_skipped` | 图文笔记被正确识别 |
| `test_empty_state_returns_none` | 状态缺失时安全返回 None |
| `test_video_via_api_fallback` | SSR 没有时走接口兜底 |
| `test_image_note_via_api_fallback` | 接口兜底也能识别图文 |
| `test_api_fallback_ignores_other_notes` | 不被“相关推荐”里别人的视频误导 |
| `test_collect_merges_api_and_dom` | 接口 + DOM 两路合并去重 |
| `test_download_and_resume` | 下载成功 + 重跑跳过 |
| `test_download_failure_recorded` | 失败写进 `failed` 桶 |

> **可复用思路**：抓取类程序测的是“解析器能不能读懂某种数据形态”，
> 不是“网站今天有没有改版”。用 Mock 页面固化数据形态，测试就稳定了；
> 站点真改版时，换一个 `_detail_html`  fixture 就能测新结构。

## 4. GUI 回归测试：专治“看不见的 bug”

### `test_finish_once.py`

验证完成提示只触发一次。它会驱动 `GuiBridge` 模拟一轮任务，
确认 `finish_run_id` 在 `_reset()` 时递增、`_finalize()` 时写回，且第二轮不会复用第一轮的 ID。

### `test_toast_flash.py`

在真实 JS 环境里跑前端 `toast()` 逻辑，模拟连续多次调用，
验证只保留一个 `setTimeout` 句柄（旧句柄被 `clearTimeout` 撤销）。

这类 bug 手工测很难稳定复现——要靠特定时序才会闪烁。
写成回归测试之后，任何一次“顺手改一下前端”都能被拦住。

## 5. 排错手册：按错误码和现象定位

### 300031 —— “当前笔记暂时无法浏览”

本质：详情页 URL 缺有效 `xsec_token` 或触发风控。

排查顺序：

1. 链接是不是从 App 分享来的？手打用户 ID 没有 token
2. `state.json` 里 `failed` 的原因是不是“详情解析失败”
3. 调大 `--delay` 到 3
4. 重新从 App 分享主页链接（换新 token）
5. 换网络环境

工具已内置对策：详情页携带主页 SSR 里的新鲜 token + 300031 自动重试一次。

### 300012 —— “IP存在风险”

IP 级风控，和 Cookie 无关。实测短时间连续多次访问必中，登录态也会被拦。
对策：停止访问 15–30 分钟冷却、换网络、或降频。不要反复重试——越试越久。

### 登录态“假成功”

现象：日志说“已检测到保存的登录状态”，但实际跳二维码。

根因：profile 被复制过。Chrome Cookie 用 App-Bound Encryption，与原始路径/用户绑定，
`cp -r` 备份再恢复会导致 Cookie 解不开。**备份 profile 没有意义**。
对策：删掉 `.xhs_profile/` 重新扫码。

### 收集到 0 篇

依次检查：

1. 账号是否私密
2. 是否弹出滑块验证码（需要在浏览器里手动完成）
3. 登录是否失效
4. 加 `--dump-api -v` 看接口巡检日志——站点改版时这是适配依据

### GUI 点开始没反应

看右侧日志。最常见是登录失效，此时会弹二维码窗口。

### 无头模式被跳登录页

实测无头访问会被风控重定向。三条路：

1. 先非无头跑一次登录，之后无头复用登录态
2. 用 `--cookie` 注入 Cookie
3. 无头 + `--qr-screenshot` 保存二维码截图给用户扫

### WebView2 相关错误 / 界面空白

Win10/11 一般随 Edge 预装 WebView2；缺失时去微软官网装 Evergreen 运行时。

## 6. 诊断开关

| 开关 | 用途 |
| --- | --- |
| `-v` / `--verbose` | DEBUG 日志，看 SSR 提取失败的具体返回值 |
| `--dump-api` | 打印页面发起的所有 API 路径（去重），站点改版诊断用 |
| `--max N` | 只处理 N 篇，快速复现问题 |
| `--list-only` | 只收集不下载，区分“收集问题”和“下载问题” |

排错时的标准收敛顺序：

```
--list-only --max 2 -v   →  先确认收集环节
        ↓ 收集正常
去掉 --list-only，保留 --max 2  →  确认详情页解析和下载
        ↓ 都正常
去掉 --max，全量跑
```

## 动手实验

1. 故意把 `pick_best_stream()` 里的 `codec_rank` 改成 `{"h265": 0, "h264": 1}`，
   跑 `python tests/test_unit.py`，看哪个用例变红。
2. 在 `_detail_html()` 里加一个新字段，确认集成测试仍能通过——
   这验证提取层的容错性。
3. 制造一个损坏的 `state.json`，跑 `test_unit.py`，确认 `test_load_corrupt` 覆盖了这个场景。
4. 手动触发一次 300012（短时间内连续访问同一主页多次），
   观察恢复需要多久——这个数据对设置 `--delay` 默认值有参考价值。

---

## 小结

- 四层测试各司其职：纯函数 / Mock 集成 / GUI 逻辑回归 / GUI 端到端
- 集成测试用本地假页面 + 真浏览器，稳定且不依赖目标站点
- `finish_run_id` 和 toast 定时器这两类时序 bug 必须靠回归测试守着
- 排错按错误码分类：300031 是 token/风控，300012 是 IP 风控，两者对策不同
- 收敛顺序：先 `--list-only --max 2`，再逐步放开

最后一篇：把这些经验整理成可复用的检查清单。
